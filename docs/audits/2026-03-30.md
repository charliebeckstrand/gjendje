# Audit — 2026-03-30

Focus: v1.5.0 primitives (`channel`, `signal`, `when`, `resource`) after merging
main into `claude/plan-1.5.0-features-A1oO1`. All prior audit items are resolved.

---

## Severity: High

### 1. `resource()` — no fetch cancellation mechanism

**File:** `src/resource.ts:131-148`

When `refetch()` is called (or triggered by dep changes) while a previous fetch is
still in-flight, the stale promise's `.then()` handlers remain attached. The result
is correctly ignored via the `fetchId` guard, but:

- The old fetch function continues running to completion (network request, DB query, etc.)
- There is no way for the user to cancel in-flight work (no `AbortSignal` passed to `fn`)
- Rapid refetches cause N concurrent fetches where only the last one matters

This is a **design gap**, not a crash bug — but it can cause real performance issues
and unexpected side effects (e.g., a POST inside a "fetch" function runs N times).

**Recommendation:** Add an optional `AbortSignal` parameter to the fetch function
signature. Create a new `AbortController` on each refetch and abort the previous one.

- [ ] Add AbortSignal support to resource fetch function

---

### 2. `resource()` — destroyed resources retain promise callbacks

**File:** `src/resource.ts:131-148, 164-176`

When `destroy()` is called while a fetch is in-flight, the promise `.then()` handlers
are never detached. They hold closures over `dataState`, `loadingState`, `errorState`,
`destroyed`, and `fetchId`. The `destroyed` guard on line 133/141 prevents state
mutations, but the callbacks (and their closures) persist until the promise settles.

If the promise never settles (e.g., a hung network request), these references leak
permanently.

**Recommendation:** Use AbortController (from finding #1) and abort in `destroy()`.
Alternatively, null out closure references after destroy.

- [ ] Prevent promise callback retention after destroy

## Severity: Medium

### 3. `fromSignal()` — exception during subscribe leaks the signal counter

**File:** `src/signal.ts:85-96`

If `signal.subscribe()` throws, the function correctly clears listeners and re-throws.
However, the `signalCounter` was already incremented (line 73) and the `instanceKey`
is consumed. This is harmless for correctness but means signal keys have gaps after
errors. More importantly, if the external signal's `subscribe()` partially succeeded
(added a listener internally before throwing), there's no way to remove it since
`unsubscribe` was never assigned.

- [ ] Review whether partial-subscribe cleanup is needed

### 4. `resource()` — no deduplication of identical fetch results

**File:** `src/resource.ts:135-138`

`dataState.set(result)` always fires even if the new result is identical to the
previous one. Unlike `state()` which has `isEqual` support, `resource()` has no
option to suppress redundant notifications when fetch returns the same data.

This can cause unnecessary re-renders in framework bindings (React, Vue, Svelte).

- [ ] Consider adding `isEqual` option to `ResourceOptions`

## Severity: Low

### 5. `when()` — empty dependencies array never settles

**File:** `src/when.ts:43-66, 123`

If `when([], () => false)` is called with an empty deps array and a predicate
that returns false, the returned promise never settles (no subscriptions to
trigger `onChange`, so predicate is never re-evaluated). Without `timeout` or
`signal`, this silently hangs forever.

This is technically correct behavior (there are no deps to watch), but it's a
usage footgun that could be caught with a warning or documented explicitly.

- [ ] Consider warning or documenting empty-deps behavior

### 6. `fromSignal()` — missing test coverage for `peek()` and promise properties

**File:** `src/signal.ts:104-118, 128-130`

The `peek()` method, `ready`, `settled`, and `hydrated` promise properties are
implemented but have no dedicated tests. While `peek()` is trivially equivalent
to `get()` for memory-scoped instances, and the promises all return `RESOLVED`,
they should have explicit tests to prevent regressions.

- [ ] Add tests for `fromSignal` peek() and promise properties

### 7. Missing test: `when()` with both timeout and abort signal racing

**File:** `src/when.ts`

No test verifies behavior when both `timeout` and `signal` options are provided
and fire near-simultaneously. The `settled` guard (line 92) should handle this
correctly, but there's no explicit test confirming the first-wins semantics.

- [ ] Add test for timeout + abort signal race

### 8. Missing test: `resource()` destroy while fetch is in-flight

**File:** `src/resource.ts`

No test explicitly verifies that calling `destroy()` while a fetch promise is
pending correctly prevents state updates when the promise eventually resolves.
The `fetchId` and `destroyed` guards handle this, but it should be tested.

- [ ] Add test for destroy-during-fetch scenario
